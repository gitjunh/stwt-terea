# 클라이언트 요구 기록

클라이언트의 말과 구현 시작 허락은 서로 다른 기록이다. 둘을 한 파일에 섞으면 수정 요청이 컨펌으로 읽힌다.

## 요구 파일

`_workspace/01_client-liaison_requirements.md`를 다음 구조로 유지한다.

```markdown
# 요구사항
- 대상 URL:
- 관련 정보:
- 사이트 식별자:

## 확정된 요구
- R1. (클라이언트가 말한 문장을 인용) — 반영 내용

## 아직 정하지 않은 것
- Q1. 질문

## 제안만 된 개선
- 제안과, 아직 확정이 아니라는 표시

## 철회
- 철회한 요구 번호와 클라이언트의 문장
```

- 요구 번호는 지우지 않는다. 바뀌면 같은 번호 아래에 새 문장을 추가한다.
- 관련 정보 경로가 저장소 안 파일이면 그 경로를 적는다. 샘플을 기본 대상으로 가정하지 않는다.
- URL과 문서가 모두 적히기 전에는 설계 시작을 요청하지 않는다.

## 컨펌 파일

`_workspace/04_client-liaison_confirmation.md`는 요구와 따로 둔다.

```markdown
# 컨펌
- status: pending
- 클라이언트 문장: ""
- 범위: 요구, 페이지 설계, 시각 명세, 단계 목록의 경로
```

`status`는 `pending`, `confirmed`, `revised`만 쓴다.

- 구현을 시작해도 된다는 뜻의 문장만 `confirmed`로 적는다. 예: "이 설계대로 구현해 줘", "컨펌합니다", "이대로 진행해".
- 칭찬과 수정이 함께 있으면 `revised`다. 수정 문장을 요구 파일에 새 번호로 넣는다.
- 침묵, 일부 화면만 괜찮다는 말, 질문만 있는 답은 `pending`으로 둔다.

## 전달 문안

`_workspace/01_client-liaison_reply.md`에는 클라이언트가 다음에 답할 내용만 쓴다. 설계 파일 전체를 붙이지 않고, 결정이 필요한 차이와 질문만 적는다.
